# 🌐 NEXUS — Network of EXperts, Unified in Strategy

## 멀티 에이전트 오케스트레이션을 위한 Agency의 완전한 운영 플레이북

> **NEXUS**는 Agency의 독립적인 AI 전문가들을 하나로 동기화된 지능 네트워크로 바꿉니다. 이것은 프롬프트 모음집이 아니라, Agency를 어떤 프로젝트·제품·조직에서든 전력 증폭기로 만드는 **배치 교리**입니다.

## 1. 전략적 기반

### 1.1 NEXUS가 해결하는 문제

개별 에이전트는 강력합니다. 하지만 조율이 없으면 다음과 같은 결과가 나옵니다:
- 서로 충돌하는 아키텍처 결정
- 부문 간 중복 작업
- 핸드오프 경계에서의 품질 공백
- 공유 컨텍스트와 조직적 기억의 부재

**NEXUS는 다음을 정의해 이런 실패 양상을 없앱니다:**
- 각 단계에서 **누가** 활성화되는가
- **무엇을** 만들고 누구를 위해 만드는가
- **언제** 누구에게 인계하는가
- 진행 전에 품질을 **어떻게** 검증하는가
- 각 에이전트가 **왜** 파이프라인에 존재하는가 (무임승차는 없습니다)

### 1.2 핵심 원칙

| 원칙 | 설명 |
|-----------|-------------|
| **파이프라인 정합성** | 품질 게이트를 통과하지 않으면 어떤 단계도 넘어가지 않습니다 |
| **컨텍스트 연속성** | 모든 핸드오프가 전체 컨텍스트를 함께 전달합니다 — 맨바닥에서 시작하는 에이전트는 없습니다 |
| **병렬 실행** | 독립적인 워크스트림을 동시에 돌려 일정을 압축합니다 |
| **주장보다 증거** | 모든 품질 평가에는 단언이 아닌 증거가 필요합니다 |
| **빠른 실패, 빠른 수정** | 에스컬레이션 전까지 과업당 최대 3회 재시도합니다 |
| **단일 진실 공급원** | 하나의 정본 명세, 하나의 과업 목록, 하나의 아키텍처 문서 |

### 1.3 부문별 에이전트 명단

| 부문 | 에이전트 | NEXUS에서의 주 역할 |
|----------|--------|--------------------|

## 3. Phase 0 — 정보 수집 및 디스커버리

> **목표**: 자원을 투입하기 전에 판을 이해합니다. 문제가 검증되기 전에는 아무것도 만들지 않습니다.

### 3.1 활성 에이전트

| 에이전트 | 단계 내 역할 | 주 산출물 |
|-------|--------------|----------------|
| **Trend Researcher** | 시장 정보 수집 리드 | TAM/SAM/SOM이 포함된 시장 분석 리포트 |
| **Feedback Synthesizer** | 사용자 니즈 분석 | 페인 포인트가 정리된 피드백 종합 리포트 |
| **UX Researcher** | 사용자 행동 분석 | 퍼소나와 여정 지도가 포함된 리서치 결과 |
| **Analytics Reporter** | 데이터 환경 평가 | 활용 가능한 시그널을 담은 데이터 감사 리포트 |
| **Legal Compliance Checker** | 규제 스캔 | 컴플라이언스 요구사항 매트릭스 |
| **Tool Evaluator** | 기술 환경 조사 | 기술 스택 평가서 |

### 3.2 병렬 워크스트림

```
워크스트림 A: 시장 정보                     워크스트림 B: 사용자 정보
├── Trend Researcher                       ├── Feedback Synthesizer
│   ├── 경쟁 구도                          │   ├── 멀티채널 피드백 수집
│   ├── 시장 규모 추정 (TAM/SAM/SOM)       │   ├── 감성 분석
│   └── 트렌드 라이프사이클 매핑           │   └── 페인 포인트 우선순위화
│                                          │
├── Analytics Reporter                     ├── UX Researcher
│   ├── 기존 데이터 감사                   │   ├── 사용자 인터뷰/설문
│   ├── 시그널 식별                        │   ├── 퍼소나 정의
│   └── 기준선 지표                        │   └── 여정 지도 작성
│                                          │
└── Legal Compliance Checker               └── Tool Evaluator
    ├── 규제 요구사항                          ├── 기술 평가
    ├── 데이터 처리 제약                       ├── 구축 vs 구매 분석
    └── 관할권 매핑                            └── 연동 타당성 검토
```

### 3.3 Phase 0 품질 게이트

**게이트 키퍼**: Executive Summary Generator

| 기준 | 임계값 | 필요한 증거 |
|-----------|-----------|-------------------|
| 시장 기회 검증 | TAM > 최소 성립 기준 | 출처가 포함된 Trend Researcher 리포트 |
| 사용자 니즈 확인 | 검증된 페인 포인트 3개 이상 | Feedback Synthesizer + UX Researcher 데이터 |
| 규제 경로 명확 | 발목 잡는 컴플라이언스 이슈 없음 | Legal Compliance Checker 매트릭스 |
| 데이터 기반 평가 완료 | 핵심 지표 식별 | Analytics Reporter 감사 결과 |
| 기술 타당성 확인 | 스택 검증 완료 | Tool Evaluator 평가서 |

**산출물**: 경영진 요약 (500단어 이하, SCQA 포맷) → 결정: GO / NO-GO / PIVOT

## 4. Phase 1 — 전략 및 아키텍처

> **목표**: 코드를 한 줄도 쓰기 전에 무엇을 만들지, 어떤 구조로 만들지, 성공이 어떤 모습인지 정의합니다.

### 4.1 활성 에이전트

| 에이전트 | 단계 내 역할 | 주 산출물 |
|-------|--------------|----------------|
| **Studio Producer** | 전략적 포트폴리오 정렬 | 전략 포트폴리오 플랜 |
| **Senior Project Manager** | 명세를 과업으로 변환 | 종합 과업 목록 |
| **Sprint Prioritizer** | 기능 우선순위화 | 우선순위가 매겨진 백로그 (RICE 점수) |
| **UX Architect** | 기술 아키텍처 + UX 기반 | 아키텍처 명세 + CSS 디자인 시스템 |
| **Brand Guardian** | 브랜드 아이덴티티 시스템 | 브랜드 기반 문서 |
| **Backend Architect** | 시스템 아키텍처 | 시스템 아키텍처 명세 |
| **AI Engineer** | AI/ML 아키텍처 (해당 시) | ML 시스템 설계 |
| **Finance Tracker** | 예산 및 자원 계획 | ROI 전망이 포함된 재무 계획 |

### 4.2 실행 순서

```
STEP 1: 전략 프레이밍 (병렬)
├── Studio Producer → 전략 포트폴리오 플랜 (비전, 목표, ROI 목표치)
├── Brand Guardian → 브랜드 기반 (목적, 가치, 비주얼 아이덴티티 시스템)
└── Finance Tracker → 예산 프레임워크 (자원 배분, 비용 전망)

STEP 2: 기술 아키텍처 (병렬, STEP 1 이후)
├── UX Architect → CSS 디자인 시스템 + 레이아웃 프레임워크 + UX 구조
├── Backend Architect → 시스템 아키텍처 (서비스, 데이터베이스, API)
├── AI Engineer → ML 아키텍처 (모델, 파이프라인, 추론 전략)
└── Senior Project Manager → 과업 목록 (명세 → 과업, 정확한 요구사항)

STEP 3: 우선순위화 (순차, STEP 2 이후)
└── Sprint Prioritizer → 스프린트 배정이 포함된 RICE 점수 백로그
    ├── 입력: 과업 목록 + 아키텍처 명세 + 예산 프레임워크
    ├── 출력: 의존 관계 지도가 포함된 우선순위 스프린트 계획
    └── 검증: Studio Producer가 전략적 정렬을 확인
```

### 4.3 Phase 1 품질 게이트

**게이트 키퍼**: Studio Producer + Reality Checker (양측 승인)

| 기준 | 임계값 | 필요한 증거 |
|-----------|-----------|-------------------|
| 아키텍처가 모든 요구사항을 포괄 | 명세 커버리지 100% | Senior PM 과업 목록과 교차 대조 |
| 브랜드 시스템 완비 | 로고, 색상, 타이포그래피, 보이스 정의 완료 | Brand Guardian 산출물 |
| 기술 타당성 검증 | 모든 구성 요소에 구현 경로 존재 | Backend Architect + UX Architect 명세 |
| 예산 승인 | 조직 제약 범위 내 | Finance Tracker 계획 |
| 스프린트 계획의 현실성 | 벨로시티 기반 추정 | Sprint Prioritizer 백로그 |

**산출물**: 승인된 아키텍처 패키지 → Phase 2 활성화

## 5. Phase 2 — 기반 구축 및 스캐폴딩

> **목표**: 이후 모든 작업이 의존하는 기술적·운영적 토대를 만듭니다. 근육을 붙이기 전에 골격을 세웁니다.

### 5.1 활성 에이전트

| 에이전트 | 단계 내 역할 | 주 산출물 |
|-------|--------------|----------------|
| **DevOps Automator** | CI/CD 파이프라인 + 인프라 | 배포 파이프라인 + IaC 템플릿 |
| **Frontend Developer** | 프로젝트 스캐폴딩 + 컴포넌트 라이브러리 | 앱 골격 + 디자인 시스템 구현 |
| **Backend Architect** | 데이터베이스 + API 기반 | 스키마 + API 스캐폴드 + 인증 시스템 |
| **UX Architect** | CSS 시스템 구현 | 디자인 토큰 + 레이아웃 프레임워크 |
| **Infrastructure Maintainer** | 클라우드 인프라 세팅 | 모니터링 + 로깅 + 알림 |
| **Studio Operations** | 프로세스 세팅 | 협업 도구 + 워크플로 |

### 5.2 병렬 워크스트림

```
워크스트림 A: 인프라                       워크스트림 B: 애플리케이션 기반
├── DevOps Automator                      ├── Frontend Developer
│   ├── CI/CD 파이프라인 (GitHub Actions) │   ├── 프로젝트 스캐폴딩
│   ├── 컨테이너 오케스트레이션           │   ├── 컴포넌트 라이브러리 세팅
│   └── 환경 프로비저닝                   │   └── 디자인 시스템 통합
│                                         │
├── Infrastructure Maintainer             ├── Backend Architect
│   ├── 클라우드 자원 프로비저닝          │   ├── 데이터베이스 스키마 배포
│   ├── 모니터링 (Prometheus/Grafana)     │   ├── API 스캐폴드 + 인증
│   └── 보안 하드닝                       │   └── 서비스 통신 레이어

## 6. Phase 3 — 구현 및 반복

> **목표**: 끊임없는 Dev↔QA 루프로 기능을 구현합니다. 모든 과업은 다음 과업이 시작되기 전에 검증됩니다. 작업량의 대부분이 여기서 발생합니다.

### 6.1 Dev↔QA 루프

NEXUS의 심장입니다. Agents Orchestrator가 **과업 단위 품질 루프**를 관리합니다:

```

│  │ 에이전트  │    │ Collector│    │                   │   │
│  │           │    │ (QA)     │    │ PASS → 다음 과업  │   │
│  │ 과업 N    │    │          │    │ FAIL → 재시도(≤3) │   │
│  │ 구현      │    │ 과업 N   │    │ BLOCKED → 에스컬  │   │
│  │           │◀───│ 테스트   │◀───│                   │   │
│  └──────────┘    └──────────┘    └──────────────────┘   │
│       ▲                                    │             │
│       │            QA 피드백               │             │
│       └────────────────────────────────────┘             │
│                                                          │
│  Orchestrator가 추적하는 것: 시도 횟수, QA 피드백,       │

## 7. Phase 4 — 품질 및 하드닝

> **목표**: 마지막 품질 관문입니다. Reality Checker의 기본 판정은 "NEEDS WORK"입니다. 압도적인 증거로 프로덕션 준비 상태를 입증해야 합니다.

| 에이전트 | 단계 내 역할 | 주 산출물 |
|-------|--------------|----------------|
| **Reality Checker** | 최종 통합 테스트 (기본 판정은 NEEDS WORK) | 현실 기반 통합 리포트 |
| **Evidence Collector** | 전면적인 시각 증거 수집 | 스크린샷 증거 패키지 |
| **Performance Benchmarker** | 부하 테스트 + 최적화 | 성능 인증서 |
| **API Tester** | 전체 API 회귀 테스트 | API 테스트 리포트 |
| **Test Results Analyzer** | 품질 지표 집계 | 품질 지표 대시보드 |
| **Legal Compliance Checker** | 최종 컴플라이언스 감사 | 컴플라이언스 인증서 |

### 7.2 하드닝 순서

```
STEP 1: 증거 수집 (병렬)
├── Evidence Collector → 전체 스크린샷 세트 (데스크톱, 태블릿, 모바일)
├── API Tester → 전체 엔드포인트 회귀 테스트
├── Performance Benchmarker → 예상 트래픽 10배로 부하 테스트
└── Legal Compliance Checker → 최종 규제 감사

STEP 2: 분석 (병렬, STEP 1 이후)
├── Test Results Analyzer → 모든 테스트 데이터를 품질 대시보드로 집계
├── Workflow Optimizer → 남아 있는 프로세스 비효율 식별
└── Infrastructure Maintainer → 프로덕션 환경 검증

STEP 3: 최종 판정 (순차, STEP 2 이후)
└── Reality Checker → 통합 리포트
    ├── 이전 QA 결과 전체를 교차 검증
    ├── 스크린샷 증거와 함께 완전한 사용자 여정 테스트
    ├── 명세 준수 여부를 항목별로 확인
    ├── 기본 판정: NEEDS WORK
    └── 모든 기준에 걸쳐 압도적인 증거가 있을 때만 READY
```

### 7.3 Phase 4 품질 게이트 (최종 게이트)

**게이트 키퍼**: Reality Checker (단독 권한)

| 기준 | 임계값 | 필요한 증거 |
|-----------|-----------|-------------------|
| 사용자 여정 완결 | 모든 핵심 경로 동작 | 엔드투엔드 스크린샷 |
| 기기 간 일관성 | 데스크톱 + 태블릿 + 모바일 | 반응형 스크린샷 |
| 성능 인증 | P95 < 200ms, 가동률 > 99.9% | 부하 테스트 결과 |
| 보안 검증 | 치명적 취약점 0건 | 보안 스캔 리포트 |
| 컴플라이언스 인증 | 모든 규제 요구사항 충족 | Legal Compliance Checker 리포트 |
| 명세 준수 | 명세 요구사항 100% | 항목별 검증 결과 |

**판정 옵션**:
- **READY** — 출시 진행 (첫 시도에 나오는 일은 드뭅니다)
- **NEEDS WORK** — 구체적인 수정 목록과 함께 Phase 3으로 회귀 (예상되는 결과)
- **NOT READY** — 중대한 아키텍처 문제, Phase 1/2로 회귀

**예상 결과**: 첫 구현은 보통 2~3회의 수정 사이클이 필요합니다. B/B+ 등급은 정상이며 건강한 신호입니다.
