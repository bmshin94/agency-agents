# 🚨 런북: 인시던트 대응

> **모드**: NEXUS-Micro | **기간**: 수 분에서 수 시간 | **에이전트**: 3~8

---

## 시나리오

프로덕션에서 무언가 깨졌습니다. 사용자가 영향을 받고 있습니다. 대응 속도가 중요하지만, 제대로 하는 것도 중요합니다. 이 런북은 감지부터 포스트모템까지를 다룹니다.

## 심각도 분류

| 레벨 | 정의 | 예시 | 대응 시간 |
|-------|-----------|----------|--------------|
| **P0 — 치명적** | 서비스 완전 중단, 데이터 유실, 보안 침해 | 데이터베이스 손상, DDoS 공격, 인증 시스템 장애 | 즉시 (전원 투입) |
| **P1 — 높음** | 주요 기능 장애, 심각한 성능 저하 | 결제 처리 중단, 에러율 50% 이상, 지연 시간 10배 | 1시간 미만 |
| **P2 — 중간** | 사소한 기능 장애, 우회 방법 존재 | 검색 동작 불가, 비핵심 API 에러 | 4시간 미만 |
| **P3 — 낮음** | 외형상 문제, 경미한 불편 | 스타일 버그, 오타, 사소한 UI 결함 | 다음 스프린트 |

## 심각도별 대응 팀

### P0 — 치명적 대응 팀
| 에이전트 | 역할 | 조치 |
|-------|------|--------|
| **Infrastructure Maintainer** | 인시던트 커맨더 | 범위 파악, 대응 조율 |
| **DevOps Automator** | 배포/롤백 | 필요 시 롤백 실행 |
| **Backend Architect** | 근본 원인 조사 | 시스템 문제 진단 |
| **Frontend Developer** | UI 측 조사 | 클라이언트 측 문제 진단 |
| **Support Responder** | 사용자 커뮤니케이션 | 상태 페이지 갱신, 사용자 공지 |
| **Executive Summary Generator** | 이해관계자 커뮤니케이션 | 실시간 경영진 업데이트 |

### P1 — 높음 대응 팀
| 에이전트 | 역할 |
|-------|------|
| **Infrastructure Maintainer** | 인시던트 커맨더 |
| **DevOps Automator** | 배포 지원 |
| **해당 개발 에이전트** | 수정 구현 |
| **Support Responder** | 사용자 커뮤니케이션 |

### P2 — 중간 대응
| 에이전트 | 역할 |
|-------|------|
| **해당 개발 에이전트** | 수정 구현 |
| **Evidence Collector** | 수정 검증 |

### P3 — 낮음 대응
| 에이전트 | 역할 |
|-------|------|
| **Sprint Prioritizer** | 백로그에 추가 |

## 인시던트 대응 순서

### 1단계: 감지 및 분류 (0~5분)

```
트리거: 모니터링 알림 / 사용자 신고 / 에이전트 감지

Infrastructure Maintainer:
1. 알림 확인(acknowledge)
2. 범위와 영향 파악
   - 영향받은 사용자는 몇 명인가?
   - 어떤 서비스가 영향을 받았나?
   - 데이터가 위험한 상태인가?
3. 심각도 분류 (P0/P1/P2/P3)
4. 적절한 대응 팀 소집
5. 인시던트 채널/스레드 개설

산출물: 인시던트 분류 + 대응 팀 소집 완료
```

### 2단계: 조사 (5~30분)

```
병렬 조사:

Infrastructure Maintainer:
├── 시스템 지표 확인 (CPU, 메모리, 네트워크, 디스크)
├── 에러 로그 검토
├── 최근 배포 내역 확인
└── 외부 의존성 점검

Backend Architect (P0/P1인 경우):
├── 데이터베이스 상태 확인
├── API 에러율 검토
├── 서비스 간 통신 점검
└── 장애 구성 요소 식별

DevOps Automator:
├── 최근 배포 이력 검토
├── CI/CD 파이프라인 상태 확인
├── 필요 시 롤백 준비
└── 인프라 상태 검증

산출물: 근본 원인 식별 (또는 구성 요소 단위까지 좁힘)
```

### 3단계: 완화 (15~60분)

```
의사결정 트리:

최근 배포가 원인이면:
  → DevOps Automator: 롤백 실행
  → Infrastructure Maintainer: 복구 확인
  → Evidence Collector: 수정 확인

인프라 문제가 원인이면:
  → Infrastructure Maintainer: 스케일/재시작/페일오버
  → DevOps Automator: 인프라 변경 지원
  → 복구 확인

코드 버그가 원인이면:
  → 해당 개발 에이전트: 핫픽스 구현
  → Evidence Collector: 수정 검증
  → DevOps Automator: 핫픽스 배포
  → Infrastructure Maintainer: 복구 모니터링

외부 의존성이 원인이면:
  → Infrastructure Maintainer: 폴백/캐시 가동
  → Support Responder: 사용자에게 공지
  → 외부 서비스 복구 여부 모니터링

전 과정에서:
  → Support Responder: 15분마다 상태 페이지 갱신
  → Executive Summary Generator: 이해관계자 브리핑 (P0에만)
```

### 4단계: 해결 검증 (수정 후)

```
Evidence Collector:
1. 수정으로 문제가 해결되었는지 검증
2. 정상 동작 상태의 스크린샷 증거 확보
3. 새로운 문제가 생기지 않았는지 확인

Infrastructure Maintainer:
1. 모든 지표가 정상으로 돌아왔는지 검증
2. 연쇄 장애가 없는지 확인
3. 수정 후 30분간 모니터링

API Tester (API 관련인 경우):
1. 영향받은 엔드포인트에 회귀 테스트 수행
2. 응답 시간이 정상화되었는지 검증
3. 에러율이 기준선으로 돌아왔는지 확인

산출물: 인시던트 해결 확인
```

### 5단계: 포스트모템 (48시간 이내)

```
Workflow Optimizer가 포스트모템을 주도합니다:

1. 타임라인 재구성
   - 문제는 언제 유입되었나?
   - 언제 감지되었나?
   - 언제 해결되었나?
   - 사용자 영향 총 지속 시간

2. 근본 원인 분석
   - 무엇이 실패했나?
   - 왜 실패했나?
   - 왜 더 일찍 잡히지 않았나?
   - 5 Whys 분석

3. 영향 평가
   - 영향받은 사용자
   - 매출 영향
   - 평판 영향
   - 데이터 영향

4. 재발 방지 조치
   - 어떤 모니터링이 있었다면 더 빨리 잡았을까?
   - 어떤 테스트가 있었다면 막을 수 있었을까?
   - 어떤 프로세스 변경이 필요한가?
   - 어떤 인프라 변경이 필요한가?

5. 액션 아이템
   - [조치] → [담당] → [기한]
   - [조치] → [담당] → [기한]
   - [조치] → [담당] → [기한]

산출물: 포스트모템 리포트 → Sprint Prioritizer가 재발 방지 과업을 백로그에 추가
```

## 커뮤니케이션 템플릿

### 상태 페이지 업데이트 (Support Responder)
```
[TIMESTAMP] — [SERVICE NAME] 인시던트

상태: [Investigating / Identified / Monitoring / Resolved]
영향: [사용자 영향에 대한 설명]
현재 조치: [무엇을 하고 있는지]
다음 업데이트: [다음 업데이트 예상 시점]
```

### 경영진 업데이트 (Executive Summary Generator — P0에만)
```
인시던트 브리프 — [TIMESTAMP]

상황: [서비스]가 [중단/성능 저하] 상태이며 [N명의 사용자 / 트래픽의 N%]에 영향
원인: [확인됨/조사 중] — [확인된 경우 간단한 설명]
조치: [진행 중인 작업] — 예상 완료 [시간 추정]
영향: [비즈니스 영향 — 매출, 사용자, 평판]
다음 업데이트: [Timestamp]
```

## 에스컬레이션 매트릭스

| 조건 | 에스컬레이션 대상 | 조치 |
|-----------|------------|--------|
| P0가 30분 내 해결되지 않음 | Studio Producer | 추가 자원 투입, 벤더 에스컬레이션 |
| P1이 2시간 내 해결되지 않음 | Project Shepherd | 자원 재배분 |
| 데이터 침해 의심 | Legal Compliance Checker | 규제 기관 신고 필요성 판단 |
| 사용자 데이터가 영향받음 | Legal Compliance Checker + Executive Summary Generator | GDPR/CCPA 통지 |
| 매출 영향이 $X 초과 | Finance Tracker + Studio Producer | 비즈니스 영향 평가 |
