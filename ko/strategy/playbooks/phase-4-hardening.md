# 🛡️ Phase 4 플레이북 — 품질 및 하드닝

> **기간**: 3~7일 | **에이전트**: 8 | **게이트 키퍼**: Reality Checker (단독 권한)

---

## 목표

마지막 품질 관문입니다. Reality Checker의 기본 판정은 "NEEDS WORK"이며, 압도적인 증거로 프로덕션 준비 상태를 입증해야 합니다. 첫 구현은 보통 2~3회의 수정 사이클이 필요하고 그게 건강한 흐름이기 때문에, 이 단계가 존재합니다.

## 사전 조건

- [ ] Phase 3 품질 게이트 통과 (모든 과업 QA 완료)
- [ ] Phase 3 핸드오프 패키지 수령
- [ ] 모든 기능이 구현되고 개별적으로 검증됨

## 반드시 가져야 할 마음가짐

> **Reality Checker의 기본 판정은 NEEDS WORK입니다.**
> 
> 이것은 비관이 아니라 현실주의입니다. 프로덕션 준비 상태에는 다음이 필요합니다:
> - 처음부터 끝까지 동작하는 완전한 사용자 여정
> - 기기 간 일관성 (데스크톱, 태블릿, 모바일)
> - 해피 패스가 아닌 부하 상태에서의 성능
> - "인증 붙였습니다"가 아닌 실제 보안 검증
> - 대부분이 아니라 모든 요구사항의 명세 준수
>
> 첫 시도에 B/B+ 등급이 나오는 것은 정상이고 예상된 결과입니다.

#### ⚡ Performance Benchmarker — 부하 테스트
```
[PROJECT]의 부하 테스트를 위해 Performance Benchmarker를 활성화합니다.

필요한 산출물:
1. 예상 트래픽 10배 부하 테스트:
   - 응답 시간 분포 (P50, P95, P99)
   - 부하 상태에서의 처리량
   - 부하 상태에서의 에러율
   - 자원 사용량 (CPU, 메모리, 네트워크)
2. Core Web Vitals 측정:
   - LCP (Largest Contentful Paint) < 2.5s
   - FID (First Input Delay) < 100ms
   - CLS (Cumulative Layout Shift) < 0.1
3. 데이터베이스 성능:
   - 쿼리 실행 시간
   - 커넥션 풀 사용량
   - 인덱스 효율
4. 스트레스 테스트 결과:
   - 한계점 식별
   - 점진적 성능 저하(graceful degradation) 동작
   - 과부하 이후 복구 시간

포맷: 성능 인증 리포트
기간: 2일
```

### STEP 3: 최종 판정 (5~7일차, 순차)

#### 🔍 Reality Checker — 최종 판정
```
[PROJECT]의 최종 통합 테스트를 위해 Reality Checker를 활성화합니다.

필수 절차 — 생략 금지:

1단계: 리얼리티 체크 명령
- 실제로 무엇이 만들어졌는지 확인 (ls, 주장된 기능 grep)
- 주장된 기능을 명세와 교차 확인
- 전면적인 스크린샷 캡처 수행
- STEP 1과 STEP 2의 모든 증거 검토

2단계: QA 교차 검증
- Evidence Collector 결과 검토
- API Tester 결과와 대조
- Performance Benchmarker 데이터 검증
- Legal Compliance Checker 결과 확인

3단계: 엔드투엔드 시스템 검증
- 개별 기능이 아니라 완전한 사용자 여정 테스트
- 모든 기기에서 반응형 동작 검증
- 인터랙션 플로우를 처음부터 끝까지 점검
- 실제 성능 데이터 검토

4단계: 명세 대조 리얼리티 체크
- 원본 명세의 원문을 그대로 인용
- 실제 구현 증거와 비교
- 명세와 현실 사이의 모든 간극을 기록
- 추측 금지 — 증거만

판정 옵션:
- READY: 프로덕션 준비 상태를 증명하는 압도적 증거 (첫 시도에는 드묾)
- NEEDS WORK: 수정 목록과 함께 구체적인 문제 식별 (예상되는 결과)
- NOT READY: Phase 1/2 재검토가 필요한 중대 아키텍처 문제

포맷: 현실 기반 통합 리포트
기본값: 달리 증명되지 않는 한 NEEDS WORK
```
