## 📜 행동 강령

이 프로젝트와 참여하는 모든 사람은 행동 강령을 따릅니다. 참여하신다면 아래 원칙을 지켜 주시기 바랍니다.

- **서로 존중하기**: 모든 사람을 존중으로 대하세요. 건강한 토론은 환영하지만, 인신공격은 용납되지 않습니다.
- **포용하기**: 모든 배경과 정체성을 가진 사람을 환영하고 지지하세요.
- **협력하기**: 함께 만드는 것이 혼자 만드는 것보다 낫습니다.
- **전문성 지키기**: 논의는 에이전트와 커뮤니티를 개선하는 데 집중해 주세요.

## 🎯 어떻게 기여할 수 있나요?

### 1. 새 에이전트 만들기

전문화된 에이전트 아이디어가 있으신가요? 좋습니다! 추가하는 방법은 다음과 같습니다.

1. **리포지토리를 포크합니다**
2. **적합한 디비전(division)을 고릅니다** — 또는 새로 제안하세요. 디비전은 최상위
   에이전트 디렉토리입니다(예: `engineering/`, `security/`, `gis/`, `marketing/`,
   `finance/`…). 둘러보면서 여러분의 에이전트가 어디에 어울리는지 찾아보세요. 라벨, 아이콘,
   색상까지 담긴 공식 목록은 리포지토리 루트의 [`divisions.json`](../divisions.json)이며,
   항상 최신 상태로 유지됩니다.

   > **디비전은 `divisions.json`(리포지토리 루트)으로 정의됩니다** — 디비전 집합에 대한
   > 단일 진실 공급원이며, CI에서 `scripts/check-divisions.sh`로 검증합니다.
   > **새 디비전을 제안한다는 것**은 다음을 의미합니다: 디렉토리를 만들고,
   > `divisions.json`에 항목(label/icon/color)을 추가하고, `scripts/convert.sh`와
   > `scripts/lint-agents.sh` 양쪽의 `AGENT_DIRS`에 추가하는 것입니다. 이 모든 것이
   > 일치하지 않거나 디렉토리에 에이전트 파일이 하나도 없으면 검사가 빌드를 실패시킵니다.
   >
   > 참고: `strategy/`(NEXUS 플레이북/런북 — 에이전트 프론트매터 없음)와
   > `integrations/`(`convert.sh`가 도구별로 생성하는 출력)는 디비전이 **아니며**,
   > 절대 디비전 목록에 추가해서는 안 됩니다.

3. **아래 템플릿에 따라 에이전트 파일을 만듭니다**
4. **실제 시나리오에서 에이전트를 테스트합니다**
5. **에이전트와 함께 풀 리퀘스트를 제출합니다**

### 2. 기존 에이전트 개선하기

에이전트를 더 좋게 만들 방법을 찾으셨나요? 기여를 환영합니다.

- 실제 예시와 사용 사례 추가
- 최신 패턴으로 코드 샘플 보강
- 새로운 베스트 프랙티스를 반영해 워크플로 업데이트
- 성공 지표와 벤치마크 추가
- 오타 수정, 명확성 개선, 문서 보강

### 3. 성공 사례 공유하기

이 에이전트들을 성공적으로 활용하셨나요? 이야기를 들려주세요.

- [GitHub Discussions](https://github.com/msitarzewski/agency-agents/discussions)에 글 남기기
- README에 케이스 스터디 추가하기
- 블로그 글을 써서 링크하기
- 영상 튜토리얼 만들기

### 4. 문제 신고하기

문제를 발견하셨나요? 알려 주세요.

- 이미 등록된 이슈인지 확인하세요
- 명확한 재현 단계를 제공하세요
- 사용 사례에 대한 맥락을 함께 적어 주세요
- 아이디어가 있다면 해결 방안도 제안해 주세요

### 에이전트 구조

에이전트 파일은 두 가지 의미 그룹으로 구성됩니다. 이 구성은 OpenClaw의 워크스페이스
형식에 대응되며, 다른 도구가 여러분의 에이전트를 파싱하는 데도 도움이 됩니다.

#### 페르소나 (에이전트가 누구인지)
- **Identity & Memory** — 역할, 성격, 배경
- **Communication Style** — 톤, 목소리, 접근 방식
- **Critical Rules** — 경계와 제약

#### 오퍼레이션 (에이전트가 무엇을 하는지)
- **Core Mission** — 주요 책임
- **Technical Deliverables** — 구체적인 산출물과 템플릿
- **Workflow Process** — 단계별 방법론
- **Success Metrics** — 측정 가능한 성과
- **Advanced Capabilities** — 특화된 기법

특별한 서식은 필요하지 않습니다. 페르소나 관련 섹션(정체성, 커뮤니케이션, 규칙)과
운영 관련 섹션(미션, 산출물, 워크플로, 지표)을 서로 분리해서 묶어 두기만 하면 됩니다.
`convert.sh` 스크립트가 이 섹션 헤더를 이용해 에이전트를 도구별 형식으로 자동 분할합니다.

### 에이전트 설계 원칙

1. **🎭 강한 개성**
   - 에이전트에게 분명한 목소리와 캐릭터를 부여하세요
   - "저는 도움을 주는 어시스턴트입니다"가 아니라, 구체적이고 기억에 남게
   - 예시: "저는 기본적으로 3~5개의 문제를 찾아내고 시각적 증거를 요구합니다" (Evidence Collector)

2. **📋 명확한 산출물**
   - 구체적인 코드 예시를 제공하세요
   - 템플릿과 프레임워크를 포함하세요
   - 막연한 설명이 아니라 실제 결과물을 보여 주세요

3. **✅ 성공 지표**
   - 구체적이고 측정 가능한 지표를 넣으세요
   - 예시: "3G 환경에서 페이지 로드 3초 이내"
   - 예시: "여러 계정 합산 카르마 10,000+"

4. **🔄 검증된 워크플로**
   - 단계별 프로세스
   - 현장에서 검증된 접근
   - 이론이 아니라, 실전에서 다져진 것

5. **💡 학습 메모리**
   - 에이전트가 인식하는 패턴
   - 시간이 지남에 따라 개선되는 방식
   - 세션 사이에 기억하는 것

### 외부 서비스

에이전트는 기능에 꼭 필요한 경우 외부 서비스(API, 플랫폼, SaaS 도구)에 의존할 수 있습니다.
그럴 때는 다음을 지켜 주세요.

1. **의존성을 선언하세요** — 프론트매터의 `services` 필드를 사용합니다
2. **에이전트는 혼자서도 설 수 있어야 합니다** — API 호출을 떼어내도 그 밑에 쓸 만한
   페르소나, 워크플로, 전문성이 남아 있어야 합니다
3. **벤더 문서를 복제하지 마세요** — 재현하지 말고 참조하세요.
   에이전트 파일은 시작 가이드가 아니라 에이전트처럼 읽혀야 합니다
4. **무료 티어가 있는 서비스를 선호하세요** — 기여자가 에이전트를 테스트할 수 있어야 합니다

판단 기준: *이 에이전트는 사용자를 위한 것인가, 벤더를 위한 것인가?* 서비스를 활용해
사용자의 문제를 해결하는 에이전트는 이곳에 어울립니다. 에이전트 분장을 한 서비스
퀵스타트 가이드는 어울리지 않습니다.

### 도구별 호환성

**Qwen Code 호환성**: 에이전트 본문은 동적 컨텍스트를 위한 `${variable}` 템플릿을 지원합니다(예: `${project_name}`, `${task_description}`). Qwen SubAgent는 최소한의 프론트매터만 사용합니다. `name`과 `description`만 필수이고, `color`, `emoji`, `version` 필드는 Qwen이 사용하지 않으므로 생략됩니다.

**Codex 호환성**: Codex 커스텀 에이전트는 독립적인 TOML 파일로 생성됩니다. Codex 통합은 최소한의 1:1 매핑을 유지합니다. `name`과 `description`은 프론트매터에서 복사되고, 마크다운 본문은 `developer_instructions`가 됩니다. `color`, `emoji`, `vibe`처럼 소스에만 있는 메타데이터와 지원되지 않는 기타 프론트매터 필드는 생략됩니다.

### 도구 통합 추가하기

agency-agents를 새로운 도구(CLI, 에디터, 에이전트 런타임)에 설치되게 만들고 싶으신가요? 먼저 **[Discussion을 열어 주세요](https://github.com/msitarzewski/agency-agents/discussions)** — 새 통합 플랫폼은 "먼저 논의하는" 변경에 해당합니다(아래 PR 프로세스 참고). 방향이 맞춰지면 깔끔한 통합 작업은 작습니다. 보통 **파일 5개 정도이고, 변환된 출력물 자체는 절대 포함하지 않습니다.** 방금 머지된 Mistral Vibe 통합이 그대로 베껴 쓰기 좋은 모범 사례입니다.

리포지토리 루트의 `tools.json`이 도구 집합에 대한 단일 진실 공급원이며, 아래 조각들 가운데 하나라도 어긋나면 `scripts/check-tools.sh`(CI)가 빌드를 실패시킵니다. 한번 실행해 보세요 — 일치해야 하는 모든 위치를 알려 줍니다.

**체크리스트:**

1. **`tools.json`** — `id`, `label`, `kebab`, `format`, `installKind`, `dest`에 더해 detect/version/scope 및 표시용 필드를 담은 항목을 추가합니다. 여러분 도구의 렌더링 결과가 다른 도구와 바이트 단위로 동일하다면 **기존 `format`을 재사용하세요**(예: `SKILL.md`를 사용하는 도구들은 `"format": "skill-md"`를 공유합니다 — 새 렌더러가 필요 없습니다). `installKind`는 `per-agent`, `roster`, `plugin` 중 하나로 설정합니다. [앱](https://github.com/msitarzewski/agency-agents-app)이 해당 도구의 브랜드 SVG를 제공하지 않는다면 `icon`은 `null`로 둡니다.
2. **`scripts/convert.sh`** — `convert_<tool>()`을 추가하거나(또는 공유 `format` 렌더러를 재사용) 도구 목록과 `--help`에 연결합니다.
3. **`scripts/install.sh`** — `install_<tool>()`을 추가하고 `ALL_TOOLS` + 탐지/라벨링 + `--help`에 등록합니다.
4. **`.gitignore`** — `integrations/<tool>/` 아래에 생성되는 출력물에 대한 규칙을 추가합니다. **이 단계는 필수이면서 빠뜨리기 쉽습니다.** 변환된 에이전트/스킬 파일은 `convert.sh`가 로컬에서 생성하며 **절대 커밋하지 않습니다**(아래 "항상 닫을 것들" 참고). 추적되는 파일은 `integrations/<tool>/README.md`뿐입니다. 기존 도구별 항목을 그대로 따라 작성하세요.
5. **`integrations/<tool>/README.md`** — 통합에 대한 짧은 문서입니다(모든 도구가 하나씩 갖고 있으며, 해당 도구 디렉토리에서 유일하게 커밋되는 파일입니다).
6. **`./scripts/check-tools.sh` 실행** — 반드시 통과해야 합니다. `tools.json`을 `install.sh`, `convert.sh`와 교차 검증해 빠진 부분을 표시해 줍니다.
7. **`./scripts/test-install.sh` 실행** — 반드시 통과해야 합니다. 실제 `$HOME`이 아니라
   일회용 샌드박스에 설치해 보면서 설치 스크립트의 관찰 가능한 계약을 고정합니다.
   파일이 어디에 떨어지는지, `--path`가 도구의 환경변수보다 우선하는지,
   `--division` / `--agent` / `--agents-file`이 필터링되는지, `--dry-run`이 아무것도
   쓰지 않는지, 공백이 포함된 경로도 문제없이 처리되는지를 확인합니다. CI는 Linux와 macOS에서 실행합니다.
8. **`./scripts/test-convert-outputs.sh` 실행** — 반드시 통과해야 합니다. 모든 도구의
   출력물을 스크래치 디렉토리에 다시 생성한 뒤, 문법이 아니라 *결과물*을 검사합니다.
   모든 에이전트의 description이 온전히 왕복(round-trip)하는지, 생성된 모든 파일이
   실제 YAML/TOML 파서로 파싱되는지, 각 도구가 에이전트당 정확히 하나의 출력을
   내보내는지, 그리고 모든 소스 파일이 데스크톱 앱이 읽는 방식 그대로 파싱되는지를 봅니다.
   의도적으로 변환기를 수정했다면 해당 도구 줄에 **manifest drift**가 보고되는데,
   이는 예상된 동작입니다. 무엇이 바뀌었는지 살펴보고 `--update`와 함께 다시 실행한 다음,
   갱신된 `scripts/convert-outputs.sha256`을 커밋해서 리뷰어가 영향 범위를 한눈에
   볼 수 있게 해 주세요. 매니페스트는 에이전트당 한 줄, 도구당 한 줄을 담고 있고
   해시는 모든 플랫폼에서 동일하므로(슬래시 경로, LF 줄바꿈), Windows 체크아웃에서도
   같은 파일이 생성됩니다. CI는 모든 PR에서 이를 실행합니다.

PR에 변환된 출력물(생성된 `integrations/<tool>/*` 파일)을 커밋하면, CI와 리뷰에서 이를 제거하고 대신 `.gitignore` 규칙을 추가하라고 요청할 것입니다.

### 훌륭한 에이전트란?

**훌륭한 에이전트의 특징**:
- ✅ 좁고 깊은 전문성
- ✅ 분명한 개성과 목소리
- ✅ 구체적인 코드/템플릿 예시
- ✅ 측정 가능한 성공 지표
- ✅ 단계별 워크플로
- ✅ 실제 환경에서의 테스트와 반복 개선

**피해야 할 것**:
- ❌ 일반적인 "도움을 주는 어시스턴트" 같은 개성
- ❌ "제가 도와드리겠습니다…" 식의 모호한 설명
- ❌ 코드 예시나 산출물이 없음
- ❌ 지나치게 넓은 범위(모든 걸 조금씩 하는 만능형)
- ❌ 검증되지 않은 이론적 접근

## 🔄 풀 리퀘스트 프로세스

### PR에 들어가야 할 것 (그리고 아닌 것)

머지까지 가장 빠른 길은 **마크다운 파일 하나**, 즉 새 에이전트나 개선된 에이전트입니다. 그게 가장 좋은 지점입니다.

그 이상의 작업이라면, 매끄럽게 진행하기 위한 기준은 다음과 같습니다.

#### PR로 언제나 환영
- 새 에이전트 추가(`.md` 파일 하나)
- 기존 에이전트의 내용, 예시, 개성 개선
- 오타 수정이나 문서 명확화

#### 먼저 Discussion을 시작해 주세요
- 새로운 도구, 빌드 시스템, CI 워크플로
- 아키텍처 변경(새 디렉토리, 새 스크립트, 사이트 생성기)
- 리포지토리 전반의 여러 파일을 건드리는 변경
- 새로운 통합 형식이나 플랫폼

야심 찬 아이디어를 정말 좋아합니다. [Discussion](https://github.com/msitarzewski/agency-agents/discussions)은 코드를 쓰기 전에 커뮤니티가 접근 방식에 대해 합의할 기회를 주는 것일 뿐입니다. 모두의 시간을, 특히 여러분의 시간을 아껴 줍니다.

#### 항상 닫을 것들
- **커밋된 빌드 출력물**: 생성된 파일(`_site/`, 컴파일된 에셋, 변환된 에이전트 파일)은 절대 체크인하면 안 됩니다. 사용자가 로컬에서 `convert.sh`를 실행하며, 그 출력물은 gitignore 대상입니다. 새 도구를 추가할 때 그 `.gitignore` 규칙을 추가하는 것은 여러분의 몫입니다 — [도구 통합 추가하기](#도구-통합-추가하기)를 참고하세요.
- **사전 논의 없이 기존 에이전트를 일괄 수정하는 PR** — 선의로 한 서식 정리도 다른 기여자에게 머지 충돌을 만들 수 있습니다.
- **거의 똑같은 "리스킨"**: 기존 에이전트를 찾아 바꾸기로 복제한 새 에이전트(예: 국가나 플랫폼 이름만 교체)는 진짜 새로운 전문가가 아닙니다. 제출 전에 `scripts/check-agent-originality.sh`를 실행하세요 — CI도 자동으로 실행합니다.

### 제출 전 확인

1. **에이전트를 테스트하세요**: 실제 시나리오에서 사용하고 피드백을 반영해 개선하세요
2. **템플릿을 따르세요**: 기존 에이전트의 구조에 맞추세요
3. **예시를 추가하세요**: 최소 2~3개의 코드/템플릿 예시를 포함하세요
4. **지표를 정의하세요**: 구체적이고 측정 가능한 성공 기준을 넣으세요
5. **교정하세요**: 오타, 서식 문제, 명확성을 점검하세요
6. **독창성을 확인하세요**: `./scripts/check-agent-originality.sh path/to/your-agent.md`를 실행하세요. 전체 로스터와 여러분의 에이전트를 비교해 거의 중복된 것을 표시해 줍니다(국가나 플랫폼 이름만 바꿔도 걸러냅니다). 새 에이전트는 진짜로 새로워야 합니다. 특정 시장에 맞춰 현지화한다면, 플랫폼과 전술과 예시를 찾아 바꾸기가 아니라 실제로 다르게 만들어 주세요.
7. **모든 도구에서 온전히 전달되는지 확인하세요**: `./scripts/test-convert-outputs.sh`를 실행하세요. 모든 도구의 출력물을 다시 생성해서 여러분의 에이전트가 각 변환기를 무사히 통과하는지(description 왕복, 파일 파싱, 누락 없음), 그리고 프론트매터가 데스크톱 앱이 읽는 방식대로 파싱되는지 확인합니다. 에이전트를 추가하거나 수정하면 생성되는 결과물이 바뀌므로 여러분의 에이전트 이름이 담긴 **manifest drift**가 보고됩니다. 이는 예상된 동작이며, 풀 리퀘스트에서는 **참고용**입니다. CI가 출력은 하지만 이 때문에 실패하지는 않습니다. `scripts/convert-outputs.sha256`은 전혀 손대지 않아도 됩니다. 여러분의 PR이 머지되면 메인테이너가 다시 생성합니다. (`--update`를 실행했더라도 괜찮습니다 — 매니페스트는 에이전트당 한 줄이므로 다른 사람의 PR과 충돌하지 않고, 해시는 Windows, macOS, Linux에서 동일합니다.)

이런 검사가 왜 있는지 한마디 덧붙입니다. 사람들이 이 에이전트들 위에 정말 놀라운 것들을 만들고 있고, 수천 명이 열 가지가 넘는 도구에서 매일 이들에 의지하고 있습니다. 멋진 일이지요. 그리고 그 말은, 변환기 하나의 작은 실수나 파일 하나의 엉뚱한 따옴표가 조용히 그 모두에게 한꺼번에 닿는다는 뜻입니다. 로컬에서 테스트 모음을 실행하는 것은 다운스트림의 모든 사람에게 그 흐름을 매끄럽게 유지하는 방법입니다. 1분 정도 걸리고, 그 대가로 여러분의 작업이 모든 도구에서 모두에게 작성한 그대로 전달됩니다. 한 걸음 더 내주셔서 감사합니다 — 영원히 만나지 못할 사람들에게 베푸는 진짜 친절입니다.

### PR 제출하기

1. 리포지토리를 **포크**합니다
2. **브랜치를 만듭니다**: `git checkout -b add-agent-name`
3. **변경 사항을 작성합니다**: 에이전트 파일을 추가합니다
4. **커밋합니다**: `git commit -m "Add [Agent Name] specialist"`
5. **푸시합니다**: `git push origin add-agent-name`
6. 다음 내용을 담아 **풀 리퀘스트를 엽니다**:
   - 명확한 제목: "Add [Agent Name] - [Category]"
   - 에이전트가 무엇을 하는지에 대한 설명
   - 이 에이전트가 필요한 이유(사용 사례)
   - 수행한 테스트 내용

### PR 리뷰 프로세스

1. **커뮤니티 리뷰**: 다른 기여자들이 피드백을 줄 수 있습니다
2. **반복 개선**: 피드백을 반영해 개선합니다
3. **승인**: 준비가 되면 메인테이너가 승인합니다
4. **머지**: 여러분의 기여가 The Agency의 일부가 됩니다!

## 📐 스타일 가이드

### 글쓰기 스타일

- **구체적으로**: "더 빠르게 만들기"가 아니라 "페이지 로드 60% 단축"
- **명확하게**: "UI 만들기"가 아니라 "TypeScript로 React 컴포넌트 작성"
- **기억에 남게**: 뻔한 기업식 어투가 아니라, 에이전트에게 개성을 부여하세요
- **실용적으로**: 의사 코드가 아니라 실제 코드를 넣으세요

### 서식

- **마크다운 서식**을 일관되게 사용하세요
- 섹션 헤더에 **이모지**를 넣으세요 (훑어보기가 쉬워집니다)
- 모든 코드 예시는 적절한 문법 하이라이팅과 함께 **코드 블록**으로 작성하세요
- 선택지를 비교하거나 지표를 보여 줄 때는 **표**를 사용하세요
- 강조에는 **굵게**, 기술 용어에는 `코드`를 사용하세요

### 코드 예시

```markdown
## Example Code Block

\`\`\`typescript
// 항상 포함할 것:
// 1. 문법 하이라이팅을 위한 언어 지정
// 2. 핵심 개념을 설명하는 주석
// 3. 실제로 실행되는 코드 (의사 코드 금지)
// 4. 최신 베스트 프랙티스

interface AgentExample {
  name: string;
  specialty: string;
  deliverables: string[];
}
\`\`\`
```

### 톤

- **전문적이지만 다가가기 쉽게**: 지나치게 격식 있거나 가볍지 않게
- **자신 있지만 건방지지 않게**: "혹시 이렇게 해 보실래요…"가 아니라 "이게 가장 좋은 접근입니다"
- **도움이 되지만 과잉 보호하지 않게**: 역량을 전제하고, 깊이를 제공하세요
- **개성 중심**: 각 에이전트는 고유한 목소리를 가져야 합니다
